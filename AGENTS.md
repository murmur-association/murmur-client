# AGENTS.md

Working notes for anyone changing this repository, human or agent. [README.md](README.md) says what the app does for its users. This file says how the code is built, which rules it must keep, and what is still missing.

## What this is

A Flutter light client for the Murmur chain. The node, and the protocol's source of truth, live in the sibling repository [`../murmur`](https://gitlab.com/murmur-association/murmur): `PROTOCOL.md` (wire format, consensus, test vectors), `vectors/demo-14.txt` (a small chain rebuilt byte for byte by the node's tests, copied here as `test/vectors/demo-14.txt`) and `CHANGELOG.md`. The client speaks **protocol 15** (`murmur-testnet-14`, `murmur-demo-14`). Of its compact block relay (Section 7.9) it only decodes the four messages and ignores them: it never sends `SendCompact`, so nodes keep sending it whole blocks (`NewBlock`). **Where this code and PROTOCOL.md disagree, PROTOCOL.md wins.** Section numbers in comments (for example "Section 3.6") refer to it. Don't edit `../murmur` from here: propose node changes to its owner instead.

**`murmur-testnet-14`** (node v0.15.0, genesis 2026-10-20) eases a block late beyond the slack at the same rate as a slow parent: the difficulty rule's exponent is one division (PROTOCOL.md Section 4), and `difficultyEase` is gone. Nodes also check signatures by ZIP 215; the client checks none (gap 8), and if it ever does it must use ZIP 215, not a strict check. The client moves to it with v0.8.0, straight from testnet-12: `murmur-testnet-13` (node v0.14.0: a 1 MB block cap and mentions) was never released by the client, and its changes come with testnet-14. Before them, `murmur-testnet-12` (2026-10-17, v0.7.0) committed the lists by Merkle mountain ranges, so any page of a thread or a history is proven on its own. A new network has no checkpoint for its first day: `network.dart` then says `// checkpoint: none yet`, sessions start from genesis, and `tool/refresh_checkpoint.dart` writes the first one itself (Recipes).

Targets: the web (the main one), plus Windows, Linux, macOS, Android and iOS. `web/`, `windows/`, `linux/`, `macos/`, `android/` and `ios/` are committed (the apps show as Murmur, with the app's icon, written by `tool/render_brand.dart`). The Mac app has **no App Sandbox**: it runs its own node as a child, which would inherit it, and the sandbox would keep the node from its data folder and its listening port.

## Commands

CI (`.gitlab-ci.yml`) runs `flutter gen-l10n` with a clean-diff check, `flutter analyze`, `flutter test` and a web build on every push. Run the same locally before committing:

```
flutter pub get                       # also regenerates lib/l10n/app_localizations*.dart from the ARB files
flutter analyze                       # must report no issues
flutter test test/protocol_test.dart test/threads_test.dart test/ui_test.dart   # offline, a few seconds
flutter build web --release --no-web-resources-cdn   # CanvasKit served locally
dart run tool/fetch_fallback_fonts.dart   # copies the engine's fallback fonts next to the page (rule 2)
dart run tool/serve_web.dart          # serves build/web on http://localhost:8080
dart run tool/ws_bridge.dart --node 127.0.0.1:7878   # only for nodes without --ws-port
flutter test tool/render_brand.dart   # regenerates web icons and build/brand_preview.png
flutter test tool/refresh_checkpoint.dart   # the testnet checkpoint, from the live network (before a release)
flutter test tool/check_checkpoint.dart     # what the release job checks: the shipped checkpoint, against the live network
flutter test tool/acceptance_test.dart      # the acceptance tests, in the app on this desktop (see "Acceptance tests")
dart run tool/header_bench.dart generate 100000 build/headers.bin   # a valid testnet header chain
dart run tool/header_bench.dart check build/headers.bin             # times the header checks (also in a browser: header_bench_web.dart)
```

Tests against the node use the **pinned node release** (`tool/node_release.dart`, now v0.15.0), downloaded from the node project's package registry and checked against its `SHA256SUMS`. The node's specification is its code, so the tests use the node itself rather than restating its rules. Without the download they're skipped (CI sets `MURMUR_REQUIRE_NODE`, which makes that a failure):

```
dart run tool/bundle_node.dart --for-tests    # into build/node; again after raising the pinned release
flutter test                                  # node_test.dart and local_node_test.dart run too
```

`MURMUR_NODE_BIN=<murmur-node>` uses another binary instead, such as one built from `../murmur` while a node change isn't released yet.

- **Nothing to set up or wait for.** `node_test.dart` has the node build the demo chains it needs (`murmur-node demo-chain`, through `test/support/test_node.dart`): a chain, an extension, or a heavier branch for a reorganization, built and checked with the node's own rules. It then starts the node on them through the app's `ProcessLocalNode`. Headers a test needs as objects come from syncing a client, never from the node's files.
- **What it covers:** checkpoint start, back-fill (stored, resumed, restarted), reorganizations (the node restarts on a heavier branch, and the client reconnects), state proofs and filters, the local copy, sending every kind with proven nonces, flat threads and flags, invitations; a thread and a history older than the checkpoint read from the node's index, with the same through filters on a node started with `--no-index`; public names set, replaced and cleared. The node mines to the chain's wallet, at 1% of a core (a node mining flat out at the easy demo target races ahead of its clock and stalls).
- **The protocol itself is checked against the node's vectors** in `test/vectors_test.dart`, offline: PROTOCOL.md's (transactions of every kind, a header with large nonces, work, the difficulty factors and targets, the header history root, the genesis hashes) the list roots and range proofs of Section 3.6, transactions with mentions, and the twelve-block chain of `test/vectors/demo-14.txt` (its last block holds mentions, with its filter and the node's list 4 for three addresses), rebuilt here from its transactions and nonces down to every target, commitment, hash and state entry, with the node's `Thread` and `Address` answers proven page by page (the first, one in the middle, the newest). Copy the file again when the node's changes.
- **Branches need room:** `demo-chain` spaces new blocks 2 s apart, never in the future, so a branch or extension of `n` blocks needs `n × 2 s` after the block it builds on. Without that room it refuses at once, writing nothing, and says how much earlier the chain must end. Build a chain that will get long branches with an earlier end (`TestNode.build(…, endTime:)`).
- **Read-only against a public node:** two files, both skipped without `MURMUR_NODE`, neither sending anything (never send testnet transactions from tests without the user asking).
  - `test/live_release_test.dart` is what a release waits on (`public-node-tests`, the only place CI sets `MURMUR_NODE`): sync from the shipped checkpoint, then the supply, the burn pool, an account and the fees (`checkProvenBasics`). It's **bounded**: a few requests whatever the chain's length. Keep it so; anything that grows with the chain would one day fail every release, and after a scheduled release has already pushed its tag.
  - `test/live_node_test.dart` is for runs by hand (`MURMUR_NODE=testnet-seed.murmur.info:7878 flutter test test/live_node_test.dart`): the proven state, an address's history and the local copy against a public node (`test/support/client_checks.dart`). No pipeline runs them.
- `test/support/fake_node.dart` remains for what a real node can't be made to do: answer on another protocol version, or on an address a test picks.

**Paths with an apostrophe** (for example `C:\Users\o'brien`) break `flutter test` and web builds, because Flutter pastes the path into generated Dart code. Map a drive letter to the parent folder and work from it:

## Rules the code must keep

1. **Never use the node's control port** (`--rpc-port`, 7879) from `lib/`. The client talks only to the P2P port, or to `--ws-port`. Tests may use the control port.
2. **Nothing goes to third parties.** No analytics, remote fonts, CDNs or crash reporters. The only network peer is the node the user chose, or the local bridge. Flutter web fetches from Google by default, so two settings stop it:
   - `--no-web-resources-cdn` serves CanvasKit from the page;
   - `web/flutter_bootstrap.js` sets `fontFallbackBaseUrl` to `fallback-fonts/`, which `tool/fetch_fallback_fonts.dart` fills after every web build. Pages built without that step fetch fallback fonts from fonts.gstatic.com, or lose glyphs.

   To check a build, load it in headless Edge with `--log-net-log` and list the origins. Only the page's own origin and the node may appear, apart from the browser's own traffic. Links out (`openLink`) open only on the user's tap.
3. **The chain cache needs consent.** `ChainCache` is used only when `Preferences.storageConsent == allowed`. Turning it off deletes it. The wallet seed (secure storage) and preferences are always stored.
4. **Never print, log or send a wallet seed, and never store it in the clear.** It lives encrypted in the key vault (`services/key_vault.dart`):
   - **Android, iOS and macOS:** the system's hardware key store via `biometric_storage`. Every read needs biometrics; Apple devices also accept the device passcode, while Android with "every time" allows biometrics only.
   - **Browsers:** a passkey with the WebAuthn PRF extension; its secret after the device check is the AES-GCM key. The user picks the passkey manager (on iOS, Apple Passwords or a third-party one such as Proton Pass), and not all of them support PRF. Only an explicit `prf.enabled: false` rejects one at creation; otherwise the output is asked for (already at creation, else with a get). If none comes, `PasskeyUnsupported` makes `sealSeed` ask (`VaultPrompts.passkeyUnsupported`): try another manager, use a passphrase, or cancel. The user found the old silent fallback to a passphrase confusing.
   - **Otherwise** (including browsers without PRF, such as Firefox): a passphrase, stretched with PBKDF2-SHA256 over 600,000 rounds into an AES-GCM key.

   The Wallet tab shows which one is used (`WalletController.protection`).

   `WalletController.wallet` holds only the public side (`WalletId`). `unlock()` decrypts the key for one use, **asking every time**: each signature (Compose, and funding invitations as one batch), **Show seed** and **Remove wallet**. The user chose that over an unlock window; nothing may keep it unlocked.
   - **Remove wallet** falls back to a plain destructive confirmation when it can't unlock, so a forgotten passphrase can still be replaced from the seed backup.
   - **Earlier plaintext seeds** (`murmur_wallet_seed`) move into the vault at the next unlock.
   - **The seed has two forms, the same 32 bytes:** 64 hex characters (what the node's key files hold) and 24 words, the BIP39 encoding of those bytes (`crypto/seed_phrase.dart`, tested with the standard's vectors; the word list in `seed_words.dart` is the standard English one, never to be sorted or edited). Only the encoding is BIP39's: there's no PBKDF2 step, so the words are the seed, not a password for one. Wherever a seed is asked for, either form is taken (`askSeed`, `parseSeed`), and wherever it's shown, both are (`SeedView`).
   - **A new wallet is shown its seed once, at creation** (`createWallet`, `showNewSeed` in `ui/seed.dart`): why it matters, the seed, and a box to tick before the dialog can be closed. `WalletController.create` hands back the wallet with its key for that; nothing else may use it.
   - **The seed is never offered to other apps:** copy only, no share.
   - **Invitation cards' codes are vaulted too** (the user asked for it; a code is its card's key). `InviteStore` keeps each code sealed to a public key (`sealTo`: X25519, HKDF-SHA256, AES-GCM), whose secret lies in the vault's second slot (`VaultSlot.invitations`): a record of its own, not hung on the wallet's seed, since cards stay when the wallet changes.
     - **One passphrase, or one passkey, for the app** (the user asked for it: a second passphrase for the cards was one too many). Whichever of the two records is made second takes the first's (`sealSeed(alongside:)`): the passphrase is asked for, not a new one, and must open the other record; in a browser the same passkey is asked, with a salt of the record's own. So a wallet made, or replaced, while cards are kept takes the cards' passphrase. In the device key store (phones, macOS) each keeps its own entry behind the same device check.
     - **No re-locking** (the user's choice): cards an earlier version put under a second passphrase or passkey keep it, and a new wallet beside them takes it.
     - **Listing and making cards asks nothing:** a record holds the card's address, and sealing needs only the public key. The first cards set their record up, which asks the wallet's passphrase or passkey once; if that's cancelled or wrong, nothing is kept and nothing is funded.
     - **Reading a code asks every time** (`unlockCards`): to show a card's QR code and link, to print, and to cancel (which signs with the card's key). One unlock for the selected cards.
     - **Codes earlier versions stored in the clear** are sealed at the next unlock, or when cards are next made.
     - Forgetting the passphrase leaves waiting cards unreadable: they can't be shown or cancelled any more (said when it's chosen, `passphraseNewForget`).
5. **Check before showing.** Every header is checked fully: link, proof of work, median-time-past, the difficulty rule's target, and `history_root`. Everything shown is proven against checked headers:
   - state proofs against `state_root`;
   - a page of a thread or of an address's history (the node's index) by its range proof, against the count and root the state holds for that list at the page's block;
   - an old header against the tip's `history_root`;
   - filters against `filter_hash`;
   - blocks against `merkle_root` and `filter_hash`;
   - transactions against merkle branches;
   - content against its hash and length.

   Two things can't be checked, and are shown as the node's word: `Fees`, and `TxStatus`.
6. **Byte-exact encodings.** A transaction has one encoding, signed (after the network's tag), hashed into its txid and sent; a header's hash preimage is little-endian except its 32-byte target; wire integers are big-endian; all exactly as in the Rust core. A node penalizes malformed messages. Any change to hashing or encoding needs a PROTOCOL.md test vector in `test/vectors_test.dart` or `test/protocol_test.dart`.
   - **A number in a transaction has one form** (`ByteReader.varint`): the shortest. A padded one is refused, or the client would take a transaction the node doesn't.
   - **A signature covers its network** (`NetworkInfo.tag`): sign with the tag of the network the node is on.
7. **Web integers are JavaScript doubles:**
   - `<<` and `>>` wrap at 32 bits;
   - `ByteData` has no 64-bit accessors;
   - integers are exact only up to 2^53.

   So use `~/`, `*` and `%` for anything past 32 bits, `ByteWriter.u64` and `ByteReader.u64` for u64, and `BigInt` for u128 (targets, work). **A u64 that may hold any value is never an `int`:** a header's nonce and a Hello's stay their 8 bytes from the wire to the hash (`BlockHeader.nonce`, `u64Bytes` for a small one at hand). A miner may start anywhere, and murmur-miner starts at random; read as numbers, such nonces rounded from 2^53 in a browser and wrapped from 2^63 elsewhere, the header hashed to something else, and valid blocks were refused (testnet block 27802 stopped every browser). `ByteReader.u64` now refuses 2^53 and above instead of rounding. The vectors are in `integration_test/support/header_nonce_checks.dart`, run on the VM by the unit tests and in a browser by the acceptance tests: the two failed at different values. Past bugs: `1 << 40` became 0, which froze a timer, and a 64-bit shift broke the subsidy.
8. **No user-facing text in Dart.** Strings live in `lib/l10n/app_*.arb`, in ICU format with plurals. Arabic has six plural forms. The client layer returns codes (`LinkError`, `TxProblem`, `TxStatusCode`), and `lib/ui/l10n.dart` words them. A new key goes into **all nine** ARB files. Format times with `formatTime`, `formatClock` and `formatElapsed`, and never with `toString()` in the UI.
   - **Amounts are units in the code and tokens on screen.** The chain counts in units, a million to the token; nothing but `lib/ui/l10n.dart` turns one into the other. Show an amount with `formatAmount` (tokens, up to six decimals, never the units), read one with `parseAmount`, put one in a field with `amountText`, and count things (heights, replies) with `formatCount`. An amount in an ARB string is a `String` placeholder, formatted by the caller. No amount goes through a `double`.
   - **Emphasis:** in explanations, `**key words**` in an ARB string show in bold copper (`Emphasized` in `ui/common.dart`). Each language marks its own key words, and translations keep the markers.
   - **Structure over paragraphs:** the user asked for no big blocks of text. Explain with short points, each an icon plus one emphasized line (`InfoPoint`), as in the fee card, the Invitations page and the Public name dialog. Fold details that only some want (the fee card's "Why this fee").
   - **Copper is the only accent colour.** A second colour (teal and others) was tried and rejected by the user.
9. **Salt every message.** Content is `salt(16) ‖ message`, from `Random.secure()`. The salt is never shown (`messageOf`).
10. **Keep the legal posture.** Nowhere in the app, the docs or the ARB files: token prices, value in money, returns, or buying. The testnet line says only that the tokens are for testing, in every language (`testnetLabel`).

### `MurmurClient` (lib/services/node_client.dart)

One connection to one node.
- **Connecting** (`_handshake`): a try counts only once the node is through the key exchange and has sent a Hello for this protocol version (`protocolVersion`). A node that fails anywhere before that is passed over for the name's next address: unreachable, dropping the connection, silent, or on another version. Natively the client picks untried addresses itself. On the web the browser picks, and keeps reusing the same address, so the 3 tries there only help with passing failures (see the web limit under Known gaps).
- **Reconnecting** (`_fail`, `retryAt`): after a failure retrying can fix (unreachable, closed, timeout, a tampered frame), the client connects again by itself, waiting 2 s, then 4, 8… up to a minute. The wait resets once live, and the banner counts it down. Everything fetched and checked is kept. A version mismatch, a checkpoint mismatch or a state-root mismatch is not retried, and neither is anything after the user's Disconnect.
- **Native** (`transport_io.dart`): the client dials a `host:port`. A name is resolved, and every address it returns is tried in random order (`connectFirst`), so a DNS seed works as the node. `resolveOverride` replaces DNS in tests. **Port 443 is a secure WebSocket here too** (`usesWebSocket`, `openWebSocket`): the address browsers use (`node.murmur.info:443`) works in every build. The address is still chosen here (the socket is dialled, then TLS is checked against the name), so a node that takes the connection and then fails is passed over, which a browser can't do.
- **Web** (`transport_web.dart`): the client uses `wss://` on port 443 or on an HTTPS page, and `ws://` otherwise (the local bridge).
- **Defaults:** without `--dart-define=MURMUR_NODE_HOST` and `MURMUR_NODE_PORT`, the default node is `127.0.0.1`; testnet builds set the public ones (README).

It's a `ChangeNotifier` that the UI rebuilds from (`AppBuilder`). The client handshakes with zero work and `listen_port` 0, so the node never syncs from it and never gossips its address.

**The worker.** `_work` runs one request at a time. Each `_step` does the most useful thing left, in this order:
1. header sync;
2. state proofs for watched keys;
3. message content for everything already fetched, newest first (`_missingContent`), so each batch of blocks is followed by its text and lists fill in while older blocks still arrive;
4. blocks a page, or a filter match, asked for;
5. settling own pending transactions, and GetTx for wanted txids;
6. a page of a thread or of an address's history being followed, from the node's index (`_readLists`);
7. the newest stretch of blocks a list needs;
8. checking the headers from genesis up to the checkpoint (after a checkpoint start), keeping none;
9. the filter scan for watched items (only what a node without an index left to filters);
10. one prefetch batch.

**The client never downloads the whole chain.** It used to, with a local copy, to count every balance; the chain grows for ever, and nothing shown needs it. Don't bring that back.

When nothing is left, it waits. `settled` says the worker got past what views asked for (only the check from genesis, a filter scan or prefetching left): what a short run, such as Android's background check for news, waits for. `_wake()` resumes it: views call things like `requestOlder`, `requestTx`, `requestBlock`, `watchAddress` and `account(...)`, which only record what they want and wake the worker. **Views never await the network.** Each request type has a single waiter (`_headersWaiter`, `_stateWaiter`, and so on), so two concurrent requests of the same type would clash. `feeInfo()` is the only request made from outside the worker, and it shares one in-flight future for that reason.

**Heights and indexes:**
- `_headers[i]` is height `i + 1`. It's packed (`HeaderChain`): `_headers[i]` rebuilds a `BlockHeader`, so loops over many heights read fields instead (`_headers.prevHashAt(h - 1)`, `minedBy`, `hashIs`). **What it holds doesn't grow with the chain's age:** the heights below a checkpoint take no room, and an old header fetched on its own is kept apart.
- `_low` is the lowest height from which every header up to the tip is known: 1, or near the checkpoint, and lower as a view asks for older blocks (`_extendDown`: a batch of headers by proof, then their blocks). Below it, a header is known only if something old needed it and it came by proof (`_fetchOldHeaders`). Use `_hdr(h)` only for `h >= _low`, and `headerAt(h)` otherwise.
- `_joint` is the lowest header taken in sequence and checked against the ones before it: 1, or the first of a checkpoint's context. It never moves: the check from genesis joins there, and no branch may fork below it.
- `_blocks` is aligned with `_headers` (`_BlockStore`: only the fetched ones take room); null means not fetched.
- `_top..height` is the fetched newest stretch.

**What a session holds, and what it works out again.**
- **The index of known messages** (`_messages`, a `MessageIndex`) is rebuilt only when `_messagesKey` changes: a message arrived, was mined or dropped, got its text or lost it. Not at every notification: a new header, a proof or a step of the sync is most of what happens, and every view reads the index. `_pending` and `_statuses` count their own changes for that (`_Counted`). An address's history (`_historyOf`) is cached the same way, by that key and how far its lists are read. **Anything new that the index is built from must be in that key**, or views go stale.
- **A page left open lets its oldest blocks go** (`_trimBlocks`, `maxBlocksHeld` 20,000, `maxTxsHeld` 100,000): it follows every new block, and would otherwise hold them all. What a followed thread or address holds of a dropped block, what is starred and what this device sent stay as transactions on their own (`_loose`); the rest goes with its messages' text, and is fetched again if a view reads back that far. Never the newest 200 blocks, never within ten minutes of a view asking for older blocks (`requestOlder`: someone is reading back), and never with a node that keeps no index (its blocks are the histories).
- **Not let go:** message texts of what is kept, transactions read from the index, and headers from the checkpoint up.

**Proven state.** `account()`, `provenPool`, `provenIssued`, `provenFlagged()` and `publishedAlias()` return proven values, or null until the proof arrives. Calling them also watches the key, so it's re-proven at each new tip (a name only every 100 blocks, or when a block holds a new one for it: many are watched and they rarely change). Balances and nonces come from proofs, never from counting. A history row's balance is worked back from the proven one, until a block the address mined.

**The node's index** (PROTOCOL.md Section 7.6). `watchThread` and `watchAddress` read a list a page at a time (`_ListRead`, `_readPage`): a thread's replies and flags (GetThread), what an address sent and what credited it (GetAddress). Since protocol 13 a list is committed by the root of a Merkle mountain range (`listRoot`, Section 3.6), so **every page is proven on its own**: its range proof (`verifyListRange`, the page's peaks and siblings) against the count and root of the state entry at the block the node answered for, each page at its own block. Each entry's merkle branch places it in its block. So a list is read from any place, in two requests, at any chain age and without its blocks: a thread from its first reply, or from where its reader left off, an address's history from its newest end.
- **What is read is one stretch** of the list, `lo` to `hi` (entry numbers from 1, `numbers` by txid), grown a page at a time either way: `wantLo` and `wantHi` say what a view wants, `anchor` where the first page starts (null: the newest). A stretch that reaches the list's end follows it (`wantHi` null): the entry is kept proven at the tip, and when its count grows the new entries are read forward. Asked forward, a node that gives fewer than asked gives the newest of the range, which leaves a gap: the client then asks for no more than it gave (`most`).
- **A reorganization** (`_reorgs`) drops what the lists hold of the dropped blocks, and each stretch is read again from where it began (`restart`).
- `threadComplete` and `historyPending` say whether a list is whole, and what's wanted is read. What a page brings is kept like a transaction fetched by id (`_loose`).
- **Old headers on demand** (`_fetchOldHeaders`): an entry in a block below the checked headers needs that block's header, which comes by GetHeaderProof against the tip's `history_root`. The same serves GetTx, so a reply's old thread no longer waits for the back-fill.
- **A node without the index** (`--no-index`) answers unavailable: the list falls back on filters (below) by itself.
- **It names what it reads.** GetThread and GetAddress tell the node which thread or address, where filters don't. GetState already names every account proven.
- **What others did about an address** (`_FlagRead`, `_othersLists`, `watchAddress(mentions: true)`): the flags against its messages (GetAddress list 2), the answers to its replies in other people's threads (list 3), and the messages that mention it (list 4). No state entry holds those lists, so they are read apart. Each entry is proven to be on the chain, and is shown only if it checks out against the address's own messages (a flag's target is one of them; an answer names the thread and the start of the txid of one of its replies, `answersTo`; a mention holds the address's first 8 bytes, `mentions`); that the node listed them all can't be proven. Nothing says when they grow, so their newest page is asked for again every ten blocks. The home page (for the badge), the Messages tab and an address's page ask for them. An answer to a reply older than the ones read makes the client read further back in what the address sent, until that reply is at hand. A node without an index gives none (gap 5), except mentions: they are filter items, so the client watches its own (`mentionItem`) instead.

**Filters.** With a node that keeps no index, `watchAddress` and `watchThread` add items. `_scanFilters` downloads filters (1000 per request), checks each against its header, and queues matching blocks. `historyPending(address)` says whether a matching block is still unfetched. `activityOf` yields history newest first, and stops at the first block that may match but isn't fetched yet. A filter holds each transaction's sender, a transfer's recipient, a reply's thread, and a flag's target and thread; **not who a reply pays**, so replies to a wallet's threads are found by watching the threads.

**Checkpoint start** (Section 7.7). Only when the network or the constructor has a checkpoint and nothing is cached:
1. Fetch the checkpoint block.
2. Fetch the 11 headers before it, with GetHeaderProof, checked by linkage: what the median-time-past and the next target need.
3. Take the history peaks through it.
4. Check every header after it fully.
5. `_backfillHeaders` checks every header from genesis up in the background, and must join `_joint` exactly; otherwise `checkpointMismatch` stops the client. **Each header is checked and let go:** only the last few stay, which the next is checked against. None is kept afterwards, since any old header can come by proof against the tip, and the join shows that the tip's history is the one checked from genesis. With a local copy, how far the check got is stored after each batch as a mark of a few kilobytes (`_BackfillMark`: the height, the last 11 headers, the history's peaks), so a later session resumes there (`_resumeMark`), or finds the check done. A mark that doesn't lead to the checkpoint is dropped and the check starts over from genesis (`_restartBackfill`), rather than blaming the checkpoint.

A branch that would replace the checkpoint's block is refused. A cached chain that doesn't contain the checkpoint is ignored. The testnet ships one once it is a day old (`network.dart`, refreshed with every release); the demo network can't, since every demo chain is different.

**Sending.** `checkTransaction` applies consensus rules (the network's least fee included: below it a transaction is invalid), the proven balance and Section 2.4's rules. `submit`:
1. salts the content;
2. works out what a reply or a flag names: a reply names its thread (the first message of the thread of whatever message it answers), a flag its target and, unless the target starts the thread, the thread;
3. waits until the wallet is proven at the block it signs at, or later (`_provenSince`; at most `provenTipWait`, else `checkingBalance`): a proof from an earlier block misses what the wallet sent since from another device, and its nonce would be one too few, which the node refuses (found by the acceptance tests, whose second device hit it; `node_test.dart` tries it with a client that holds an older proof);
4. signs for this network with `nextNonce`: the proven nonce, plus own transactions the proof doesn't count yet, in contiguous nonce order: pending ones, and those mined above the block the proof is from (`_notYetProven`; a proof lags a new block, and without them a reply sent right after one's thread is mined would reuse its nonce);
5. sends SubmitTx;
6. keeps the transaction in `_pending` (mine: true).

A TxStatus of invalid or refused takes the transaction out of nonce and balance accounting (`_inPlay`). Once the proven nonce passes an own pending transaction, `_settleOwnPending` asks for it by id: on the chain, it becomes a proven transaction; unknown, it was replaced and is dropped. On a reorganization, own transactions in the dropped blocks become pending again.

**Composing** (`ui/compose_page.dart`). Each entry point fixes the kind; there's no switch on the page:
- **New thread:** the Threads tab's button. Only that tab has it.
- **New transaction:** the Wallet tab's button, once there's a wallet. Also **Send** on an address's page.
- **Reply and Flag:** from a message.
- **Public name:** the Wallet tab (a Name).

**The fee follows the chain, and never changes by itself** (the user asked for both). The figures are asked again at each new block (`_loadFee`, no refresh button). The fee field takes the first suggestion, then follows the message's weight at the figures taken (`_taken`), until the user types a fee. A newer suggestion is only pointed out: "Use" and the fee field flash (`_feeMovedAt`, `FadingHighlight` with pulses), and "Use" takes it. **A reply's reward is the suggested fee** by default, nothing more (it was a fixed 1 token); a fee typed above it raises it to the `amount >= fee` floor, and a reward typed by hand stays. The summary says, lightly, when the fee isn't the suggestion (`feeBelowSuggested`, `feeAboveSuggested`): the user's choice either way, never an error. The message field capitalizes sentences on phones' keyboards (`TextCapitalization.sentences`, the system's own).

**Threads are flat** (the owner's decision for testnet-10, for the chain's size and the client's speed). A reply names its thread, not the message it answers, and **pays the thread's author, whoever it answers**: the interface must never suggest that answering someone rewards that person. Who answers whom inside a thread is not on the chain: quotes say it (below).

**A thread page runs from the oldest reply down** (`ui/thread_page.dart`): the first message, then the replies, oldest first, as a forum reads. The user tried newest first (v0.6.0) and found it unusable; don't bring it back unasked.
- **One page at a time** (`threadPage`, 500): a first visit reads the first page and opens at the top. Reaching the last reply at hand reads the page after (`readLater`, `threadHasLater`: a spinner at the foot, built only as the reader nears it); "Earlier replies", between the first message and the replies, reads the page before (`readEarlier`, `threadHasEarlier`). `threadReading(earlier:)` says which is being read. A thread opens with one page however long it is. Once the page reaches the thread's end, new replies join at the bottom.
- **Only the stretch read is shown** (`threadReplies`): a block fetched for something else may hold a later reply, which would otherwise show after a gap, and a pending reply waits until the page reaches the end.
- **Where the reader left off** (`Preferences.threadsRead`: the furthest reply that has been on screen, and its place in the thread, `threadPlace`) is where the next visit opens (`watchThread(from:)`, a little before it) and goes to. The user asked for it: the first visit's behaviour (the top) was right, the following ones should go to the last read. **Others' replies newer than that are highlighted as they come into view**, not when built (`_onScreen` measures the cards), and the highlight fades (`FadingHighlight`).
- **A page opened for one message goes to it** (`focusTxid`: a reply just sent, or one tapped in a list), in place of where the reader left off. Such a message is most often recent, so the thread is read from its newest end (`watchThread(fromEnd:)`), and back page by page if the message is older.
- **The stretch read is the page's**, one per thread: when a page opens (`move: true`, its first build only, so two pages of a thread can't take it in turns), what was read moves to where it opens if that isn't in it. A starred thread follows its end (`followEnd`, from `starredActivity`); while the page's stretch doesn't reach there, the newest page is read apart (`<root>:end`), so its news is found however long the thread.
- **The reply count in the title** is of the replies at hand, so it's left out while there are more either way.
- **The order is the chain's** (height, then place in the block), never block times: two blocks may carry the same time. `_messagesKnown` sorts what came from blocks and what came on its own (`_loose`) together.
- **An address's two lists are read the same way** (`historyPage`, `readEarlierHistory`, `historyHasEarlier`): the newest page of each, and the page before when a list reaches its end and asks. A history shows only as far down as both lists reach (`_historyFloor`): below the lowest entry of a list read in part, the other list's entries can't be put in order yet. Balances are worked back from the proven one, so they need nothing older.

**Answers and quotes.** Which reply a reply answers is on the chain since protocol 12: the owner asked that being answered in someone else's thread reach the Messages tab like on any forum, and accepted a consensus change for it (PROTOCOL.md Sections 2.1 and 2.4).
- **An Answer** is a Reply that also carries the first 4 bytes of the txid of the reply it answers. The chain treats it as a Reply in every respect and never reads those bytes. **In this code it is a `TxKind.reply` with `Transaction.answers` set**, so that nothing that handles replies knows of two kinds; only the encoding tells them apart (tag 5, `Transaction.answerTag`).
- **Sent by `submit`:** a reply to a reply is an Answer; a reply to the thread's first message is a plain Reply.
- **Text quotes** (`protocol/quote.dart`) are how replies said it before Answers: a first line `>3fa9c21e`, the same 8 hex characters. The client no longer writes them and still reads them (`quotesOf` gives an Answer's bytes first, then any the text names), so several replies can still be named by hand.

- **Which reply it means** (`quotedReply`): the oldest reply of the thread that starts so, among those before the quoting one. So a reply made later to share those characters can't take a quote over, and nothing quotes what came after it. The thread's first message is never quoted: answering it needs no quote.

- **Shown in the thread** (`_Quote` in `thread_page.dart`): the answered reply's author and first two lines above the answer, with a copper bar. **A tap goes to that reply and marks it** (`_goTo`: it is older, so further up; the page moves up until its card is built). The owner asked for that in place of a dialog. The mark fades after a moment (the user asked for it), as every highlight in a thread does. A quote of a muted author's reply shows nothing.
  - **A quote of a reply older than the ones loaded** shows as "An earlier reply (tap to load it)"; the tap reads earlier pages until it is there (`_seeking`), then goes to it. With the whole thread at hand, a quote that names no earlier reply is dropped.
- **A text quote's line is left out everywhere else** (`messageText(reply: true)`, so lists, search and the transaction page show what the reply says itself).
- **Being answered reaches the answered wallet** through the node's list of answers to an address (above): Messages lists them with the replies received, and the badge counts them. They move no tokens for that wallet (the chain credits the thread's author), so the Wallet tab doesn't show them.

**Mentions** (protocol 14 and later, PROTOCOL.md Sections 2.1, 2.4 and 3.6; the user asked for them, as on any forum). An Orphan, a Reply or an Answer names up to 4 people (`Transaction.mentions`, `maxMentions`), each by the first 8 bytes of their address (`mentionOf`). The chain carries them and never reads them; they cost their bytes in the fee (`txWeight(mentions:)`), which is also what keeps them from being spammed.
- **Written in Compose** (`ui/mentions.dart`, `MentionPicker`): typing `@` suggests people the app knows (`mentionCandidates`: the thread's people for a reply, then starred people, then names given here). Picking one writes `@name` in the text and adds them; chips show who is mentioned. Public names can't be looked up from name to address, so only known people can be mentioned. The summary lists them and says a mention is public (`mentionPublicPoint`).
- **The text is a convention, the bytes are what notify.** `@name` in a message is for the reader; what reaches the named is the 8 bytes. A message shows whom it mentions under its text (`MentionsLine`): a picture opening their page where the app knows an address that starts so (`addressOfMention`), the 8 bytes otherwise.
- **Received:** from the node's list 4 (above). Messages has a "Mentions" filter (`MessageFilter.mentioned`, on by default and added once for those whose filters were saved before), the badge counts them, and they stay marked until opened. A mention in a message its author withdrew is withdrawn with it (`mentions`). Muted senders stay hidden.

**Sign and send**, or Ctrl+Enter (Cmd+Enter on Apple), follows the same steps:
1. the form is validated;
2. `checkTransaction`, so what can't be sent is said before anything else;
3. `_SendSummary`, a full summary as the final confirmation (the user asked for it). It rebuilds with the client: the balance and what's left follow new blocks and transactions, and the same check runs again. If sending stops being possible, it shows why and disables signing. `_confirming` changes through `setState`, so the page's button comes back after the summary closes;
4. `unlockWallet`;
5. `submit`, with exactly the values the summary showed.

**Threads tab.** It shows a snapshot: `threads(upTo: height)` fixes the order at one block. Own sent messages are always included. A new snapshot is taken when the list is pulled down at its top (a `RefreshIndicator`, with mouse and touchpad drags too; the user asked for it in place of a Refresh button; the chain's own refresh is elsewhere), when the tab comes into view (`refreshToken`), and when returning from a pushed page (`RouteAware.didPopNext`). Message text is read live (`messageOrUnavailable`), because content arrives after the list.
- **A listed thread never moves** (the user asked for it). Blocks arrive newest first, so a reply can be known before its thread, which is older. `MessageIndex.missingParents` names such threads; `threads(upTo:)` asks for each by id (`requestTx`) and returns only the threads more recent than the newest such reply (`settledThreads`), until its thread arrives or the node says it has none. `threadsHeldBack` keeps the list's loading line meanwhile.
  - **A reply reserves its thread's place, however long the thread takes** (the user asked for it, after threads below a checkpoint's headers were let through and then moved): nothing less recent shows until the thread is here, even when that waits for the back-fill.
  - **Nothing shows that's as old as a block still missing** (`_unfetchedFloor`). Blocks aren't only fetched newest first (a filter match, an open page, the local copy from genesis up), and a missing block may hold threads that sort above, or a reply that bumps a thread already at hand.
  - Only what can't arrive lifts the wait: the node doesn't know the thread, or the client is disconnected and not about to retry.
- **Ties** (a block's messages share its time) are ordered by the threads themselves: the one started later first, then by txid. Never by arrival order, or the same list would differ between loads.

**Invitations** (`protocol/invite.dart`, `services/invitations.dart`, `ui/invitations_page.dart`, `ui/claim_page.dart`). A card is a wallet of its own. No protocol change is involved.
- **Making cards:** the inviter funds each card with a plain transfer: five threads at today's suggested fee for a 280-byte message, plus a claim fee. The cards' codes go into secure storage, encrypted (`InviteStore`, rule 4), before any funding is sent.
- **Claiming:** the newcomer's app (`#/invite/<code>`, or "I have an invitation") creates a wallet if needed, then moves the card's whole balance to it in one Raw transfer. The fee comes out of the card, so the newcomer spends nothing.
- **Cancelling:** the inviter can cancel a card at any time, after confirming. It's the same sweep, signed with the card's own key, so it can send anywhere. The destination (`_CancelDialog`, `ReturnTo`):
  - when every selected card was funded by the wallet here now, the tokens go back there and nothing more is asked;
  - otherwise the dialog asks, as the user wanted: back to the wallet that funded each card (`funderOf`), or to the wallet here now.

  Each option is disabled while it has no address: a funder still being looked up on the chain, or no wallet on the device. With no wallet here, a card can still be cancelled back to its funder.
- **No expiry, on purpose.** The chain has no time locks, so a date on a card would only be an app convention that another app could ignore. The user rejected that illusion of enforcement. A card works until it's claimed or cancelled; don't reintroduce an expiry without a protocol-level time lock.
- **The code:** Crockford base32 of `version(2) ‖ genesis[0..4] ‖ seed:32 ‖ sha256[0..4]`, 66 characters. Version-1 codes, which had a 2-byte expiry day after the network, still parse, with the day ignored. Typing is forgiven: case, dashes, O/0, I/L/1.
- **Status comes from the card's proven balance:** waiting, claimed, cancelled. "Invited by" is whoever funded the card, found through its filter.
- **One view** (the user asked for it; no separate cards page). It's a list of cards with checkboxes and select-all. **Print** (web) and **Cancel invitation** act on the selected cards, with one confirmation for Cancel. Each row has the card's account picture, its state and amount (with `Glyph.coin`), and a QR icon (`Glyph.qr`, not a miniature code) that, after unlocking the cards, shows the code large in a dialog over the list, with the typed code and a button to share its link. Claimed and cancelled cards fold into a second, collapsible "Claimed or cancelled (n)" list. Tapping one of those opens its details (`_InviteDetails`), read from the card's history through its filter:
  - when it was funded, and how much;
  - who claimed it (their picture and name, which open their page) and when, with what they received;
  - or, if it went to this wallet, that it was cancelled, when, and what came back.
  - New cards come selected, ready to print, and only waiting cards can be selected. The cancel confirmation always states how many cards it cancels.
  - Amounts show a coin and the number in bold (`_Amount`). The create dialog shows "Each card" and "You pay" with their explanations in small print.
- **The printed card** (`cardSheet`): an 85×55 mm business card on the app's paper tone, with a copper band on the leading edge. It carries the logo and "Murmur", the slogan (`inviteCardSlogan`, never about money or value), a faded logo as a watermark, the QR code on white with "Scan to join", "From … · n of N", and the typed code (always left-to-right). `print-color-adjust: exact` keeps the colours when printing.
- **Printing** (web only): a self-contained HTML page with SVG QR codes (`package:qr`), opened from a blob URL. Native builds copy the links instead.
- **The name on the cards** (`_FromDialog`) is asked before every print. The cards stay on the device when the wallet changes, so the wallet here now may not be the one that funded them. The options:
  - the funding wallet's address, the name given to it on this device, or its public name;
  - the current wallet's address, name or public name, offered only when it differs from the funder;
  - any text, where empty leaves the "From" line out.

  A public name can be picked once it's known (`publishedAlias`; the dialog watches the funders so their history, and so their alias, is found). An option some selected card has no value for is disabled, with the reason. One that differs between cards says so, and prints each card's own. The last choice is offered first for the rest of the session. The funder is kept in `InviteRecord.funder`; older cards find it through `inviterOf`, the oldest transfer in.
- **A card is a bearer token**, and the chain publicly links inviter → card → newcomer. Both are said in the UI.

**Notifications** (`services/news.dart`, `services/notifier.dart`, `ui/notifications*.dart`). The user asked for them on phones; there is no push, by rule 2.
- **What's news** (`newsSince`, `walletNews`, `starredMessages`): replies in the wallet's threads, answers to its replies, messages that mention it, and replies under what's starred or by starred people. The Messages and Starred badges count from the same functions. Three topics (`NotifyTopic`), each switched on apart, **all off until the user switches one on** (`Preferences.notifyTopics`); the first asks the system's permission, within the tap (browsers allow it only then).
- **Raised by the app itself** (`flutter_local_notifications`), from what it fetched and proved from the node the user chose. No push service (FCM, APNs, Web Push): those route through Google's, Apple's or the browser's servers and need a server of ours that knows what each device follows. Don't add one unasked.
- **While the app runs** (`NewsWatcher`): a check a couple of seconds after the client changes. When the app isn't in front (another window, a hidden tab, a phone's home screen), news is shown; when it is, it's only recorded as told, since the badges show it.
- **Android, while closed** (`notifications_background_io.dart`): a WorkManager job about every 15 minutes, as the system allows. A run reads the device's settings and wallet address, starts a client of its own (with the local copy, if consented), follows what news comes from, waits until `settled` for three seconds in a row (two minutes at most), tells, and disconnects. **It's skipped while the app runs** (the app's isolate answers a ping through `IsolateNameServer`): the two would share the local copy.
- **Told once** (`Preferences.notifiedUntil`, `notifiedIds`): switching the first topic on starts from now, so a wallet's past never arrives; messages back to two hours before the last told are looked at (a block may carry an earlier time than the one before), less what was told. What was seen in the app (`messagesSeen`, `starredSeen`) isn't told, and **an open tab counts as seen only while the app is in front** (`_looking` in `home_page.dart`): a phone left on the Messages tab would otherwise never be told of a reply (the acceptance tests found it). A notification's id comes from its txid, so the same message from the app and a background run shows once.
- **A system may refuse** (notifications off for the app, no desktop to show them on): the app logs it and goes on, and the news counts as told, so it isn't offered again at every check.
- **At most five at once**, newest first, then one that counts the others (`notifyMore`). Each says who (`nameFor`) and why, with the message's first line; a tap opens it in its thread (`appNavigator`, payload `/thread/<root>/<txid>`). Withdrawn and non-text messages, and muted senders, are never told. On Android the lock screen hides what they say (`NotificationVisibility.private`).
- **Where:** every platform; the bell (`NotificationsButton`, `Glyph.bell`) is in the Messages header and beside the Starred tab's lists. Apple's notification centre (iOS, macOS) is asked for permission when the first topic is switched on, and the app is its delegate (`AppDelegate`), so a tap reaches it. **iOS also checks while closed** (background app refresh, `BGTaskSchedulerPermittedIdentifiers` = `murmur-news` in Info.plist, registered in `AppDelegate`): iOS decides when, hours apart for an app rarely opened. macOS's background tasks run only while the app runs, whose watcher already tells, so none is scheduled there.

**Sharing** (`ui/share.dart`). Every link, address and hash has a `ShareButton` (`Glyph.share`) instead of a copy button.
- **Where the system has a real share sheet**, the button offers "Copy" and "Share…": Android, iOS and macOS through `share_plus`, and browsers with the Web Share API through `navigator.share`.
- **Elsewhere it simply copies.** That's Windows and Linux, where the plugin would fall back to a mail link, and Firefox on desktop.
- **A QR code where a link opens something on another device:** `ShareButton(qr:)` adds "QR code" to the menu, and `showQr` shows the link large with a share button under it to pass it on again. Addresses have it (`HashText(qr: addressLink(address))`: scanning opens the address's page) and invitation cards use the same dialog.
- **Copy and share inside the tap** (`copyText`, the menu items' `onTap`): browsers allow the clipboard and the share sheet only while the user's tap is being handled. A menu's `onSelected` comes after its closing animation, and an iPhone's Safari then refuses both, which is how "Copy" once copied nothing there. Never call them after an `await`.
- **The wallet seed** keeps a plain copy button on purpose: it must never be offered to other apps.

**Links** (`routeOfLink` in `main.dart`): `#/thread/<txid>` opens a thread over the home page (`threadInRoute`), `#/address/<address>` an address's page (`addressInRoute`), `#/invite/<code>` an invitation. An unknown root is asked for by id (GetTx). Native builds share `https://app.murmur.info/#/thread/<txid>`.

**Times:** lists show relative times (`formatAgo`: "5 min ago", the date after 30 days); detail pages show full ones (`formatTime`).

**Paging** (`ui/paged_list.dart`). A list shows a screenful plus one row, then ten more at the bottom. `fetch(n)` must be cheap for small `n`, since sources are lazy iterables over the chain. `loadingMore` plus `onNeedMore` pull older blocks.

**Cache** (`services/chain_cache*.dart`):
- Headers are saved as they are held: from genesis, or from the checkpoint's context up (each says its own height). Beside them, the back-fill's mark.
- **A session with a checkpoint always starts from it** (two requests), then takes the stored headers above it, checked like a node's (`_attachStored`). So what is held starts at the newest checkpoint however old the copy, and a copy from an older checkpoint, or from genesis, is rewritten to match.
- Blocks and content are saved as they arrive.
- Everything is re-checked on load: link, PoW, history root, checkpoint, merkle root, filter, content hash.
- A cache from another network (by genesis hash) is dropped.

**The app's own node** (`services/local_node*.dart`, desktop only). The user asked for it: a desktop app can run a Murmur node, so the user validates the chain on their own machine and keeps their own messages available.
- **The client never connects to it** (the user asked for it, after the app did and lists came up without text: this node keeps nobody else's messages). It only takes part in the network beside the app, mining or not; the client reads from the node the user chose, like every other build. Don't route the client through it unasked.
- `LocalNode` starts `murmur-node` (next to the executable, placed by `tool/bundle_node.dart`; `MURMUR_NODE_BIN` overrides it) as a child process, with the options in `localNodeArgs`:
  - `--port 127.0.0.1:0 --rpc-port 0`: local only, on free ports, so no firewall prompt and no clash with another node; the port is read from the node's startup line (`listeningPort`);
  - `--prune-content --prune-retracted --keep-author <wallet>`: it keeps nobody's content past the one-hour check except the user's own, and deletes withdrawn messages. The user wanted desktop users kept out of hosting other people's content; don't change these defaults unasked;
  - `--mine-to <wallet> --mine-cpu <n>` only when the user switches mining on;
  - `--gpu` with those, when the user switches "Mine on the graphics card" on (off by default) and `murmur-miner` is beside the node (`LocalNode.canMineOnGpu`; `tool/bundle_node.dart` copies it, and `package_desktop.dart` requires it). The node runs the miner itself, rests its processor miner while the card mines, and mines on the processor when the card can't be used. A node without the option refuses to start with it, so never pass it to a node that has no miner beside it.
- **What the card is doing comes from the node's output**, not its control port (rule 1): `gpuMiningOf` reads the `[gpu]` lines (mining on a card, not available and why, starting again), and the Chain tab's card shows them. An unavailable card leaves the switch on and says mining continues on the processor, with the node's English reason as a detail (never matched on). **No hash rate is shown:** the node gives it only through `status` on the control port.
- `LocalNodeLink` keeps it in line with the settings (`Preferences.runLocalNode`, `localNodeMining`, `localNodeCpu`) and the wallet. **Any change restarts the node** with new options: rule 1 still holds, so the app never uses its control port. It's given no client (`test/local_node_test.dart` checks what it starts and stops).
- A pid file in its data folder lets a new session stop a node left running by a crashed one (only if that pid is still a `murmur-node`). The app stops the node on exit (`AppLifecycleListener`).
- The Chain tab's card (`_LocalNodeCard`) appears only when the binary is present.
- `test/local_node_test.dart` covers the options and port parsing offline, and with `MURMUR_NODE_BIN` runs a real demo node, syncs a client from it and stops it; another real node is asked to mine on the graphics card and must say whether it does.

## Recipes

- **New protocol version:**
  1. Update `protocolVersion` and the codec in `wire.dart`.
  2. Update the models, and the network ids and genesis parameters in `network.dart` (genesis hashes are pinned in `protocol_test.dart`).
  3. Add PROTOCOL.md's vectors to `protocol_test.dart`.
  4. Raise `nodeRelease` in `tool/node_release.dart` to the node release that speaks it, run `dart run tool/bundle_node.dart --for-tests`, and run all the tests (Commands).
- **New wire message:** add the class and its encoder and decoder in `wire.dart`, and enforce its limits while decoding. Add a round trip to `protocol_test.dart`'s "messages have the node layout". Handle it in `MurmurClient._handle`: every tag must appear there, since the switch is exhaustive over a sealed class.
- **Every release refreshes the checkpoint** of each public network (not the demo network, whose chains are all different). A first session checks every header after the checkpoint before showing anything: a two-month-old checkpoint on the testnet means about 170,000 headers. The checkpoint must come from the release, never from a node or the user: a node could hand the client a fake chain's block, and the user only chooses nodes. A newer release's checkpoint that isn't in a user's local copy makes the client drop the copy and start over from it.
- **Shipping a checkpoint:** `flutter test tool/refresh_checkpoint.dart` rewrites the testnet's `checkpoint:` line in `network.dart` from the live network, without taking a node's word (`tool/checkpoint/live.dart`): every address behind `testnet-seed.murmur.info` is asked separately, by a client that starts from the checkpoint shipped now (so the chain must hold it) and checks every header back to genesis, and at least two must answer and all agree. It picks a round height a day below the lowest tip. Review and commit the one-line change (the scheduled release, below, commits it by itself once the tests pass); never write a checkpoint by hand. **A network's first is written the same way:** while the chain is under a day old the tool writes nothing and the source keeps `// checkpoint: none yet`, which the tool later replaces with the first line, from clients that checked from genesis. The release job runs `tool/check_checkpoint.dart`, which stops a release whose checkpoint isn't on the live chain or is over a week old, and one without a checkpoint once the chain is over a week old. `network_test.dart` checks its form.

## Style

- Comments say why, in plain sentences, and name the PROTOCOL.md section they follow. Public members have doc comments. Match the density of the surrounding code.
- Keep `lib/protocol/` free of Flutter imports, so it stays testable and reusable.
- Keep `flutter analyze` clean (`flutter_lints`). Don't add dependencies without a good reason: the client's security depends on how little it pulls in.

## Security model, briefly

- Transport: encrypted and integrity-protected (BIP 324-like), but **peers aren't authenticated**. A man in the middle can't forge chain data, since everything is proven against checked headers and proof of work. It can withhold data, show an older chain, or learn which accounts the client asks about.
- Filters don't reveal what the client watches. `GetState` does name the account.
- `tipLooksOld` shows a banner when the tip is more than 20 block intervals old.
- Defences still missing: several nodes (gap 1 below), and node identity pinning for a trusted node.

1. **One node only.** Section 7.7 recommends at least three, from different sources, following the heaviest valid chain and retrying requests elsewhere. `MurmurClient` would need a node pool, and a way to route each request.
2. **Little peer discovery.** Natively, a seed name such as `testnet-seed.murmur.info` works as the node: every address it resolves to is tried, through the handshake, and a lost link reconnects by itself (possibly to another of them). There's no `Addr` handling. Browsers can reach only nodes with `--ws-port`, behind TLS for `wss://`.
   - **Web limit, accepted:** in a browser, page code can't see a name's addresses or choose among them. The browser resolves the name, caches the answer, and reuses the same address. It moves on from an address that refuses or doesn't answer, but not from one that accepts the connection and then fails TLS.
   - A web client can't get past such a node by itself. Measured: 72 retries against `node.murmur.info` all went to the same broken address, while the native client reached all three nodes. `node.murmur.info` includes broken nodes on purpose, to test this.
   - **Rejected workarounds:** DNS over HTTPS (a third party), connecting by IP (TLS rejects it), per-node names (the network keeps one name). Don't reintroduce them unasked.
3. **The testnet checkpoint ages.** A first session checks every header after it before lists show (about 3,000 a second in a browser), and the gap grows by 2,880 a day, so every release refreshes it (Recipes), and the release job refuses one over a week old. Its trust rests on the chain of checkpoints back to the first, and on the testnet's nodes agreeing when it's refreshed: they're all behind one name, run by the project. Checkpoints come only with releases; users choose nodes, never checkpoints, and a running client never takes one from a node.
4. **Headers in memory no longer grow with the chain** (done 2026-10-08). `_headers` and `_backfill` are `HeaderChain`s (`lib/protocol/header_chain.dart`): 280 bytes a header (wire bytes plus hash) in one byte array, with the last 1,024 used kept as objects. What is held: the headers from the release's checkpoint up (a week of blocks, about 6 MB, more for a release left unupdated), and the old ones a view asked for. What is left:
   - **Loops over every height remain** (`historyPending`, `activityOf` and the filter scan with a node that keeps no index; `heightOfBlock`): they cost time, not memory, and only from `_low` up or with such a node.
   - **Browsing below the checkpoint costs a proof per header** (`_extendDown`, 128 at a time, each a couple of kilobytes): fine for paging back, heavy for reading a chain's whole past, which a light client shouldn't do anyway. Those headers aren't stored in the local copy, so blocks stored below the checkpoint are fetched again.
   - **A desktop app never updated** keeps its old checkpoint, and so every header since: its growth is by the release's age, not the chain's.
   - **Not measured in a browser** since the change; the web build compiles and the acceptance tests pass in Chrome.
   - **Measured before protocol 11** (2026-10-04, 232-byte headers): about 376 bytes a header in a browser, spare capacity included; about 360 µs to check one in a browser. With the new difficulty rule a check on the Dart VM takes about 75 µs (`tool/header_bench.dart`, 2026-10-08), where it took 165; the browser hasn't been measured again.
   - **Rollbacks** rebuild the header history from a copy kept every 1,024 heights (`_historyMarks`, the last 16), not from genesis: rebuilt headers compute their work again.
   - **The local copy loads packed too:** the stores hand over headers as they decode them (`storedHeaders`), and `_loadCache` checks and packs each in turn.
   - **The per-height filter maps** (`_filters`, `_filterTested`) hold an entry per block scanned, and aren't packed. They matter only with a node that keeps no index.
5. **Flags, answers and mentions received can't be proven complete.** None is in an address's proven lists. The client reads them from the node's index (GetAddress, lists 2 to 4): each is proven, their completeness can't be. Filters hold a flagged message's txid or an answer's thread, not the author concerned, so with a node that keeps no index flags and answers show only where the thread is open; mentions are filter items, so they are still found.
6. **The node's macOS release is untried here.** Node releases since v0.10.8 carry a macOS archive (`universal-apple-darwin`: one file for Apple silicon and Intel, signed ad hoc only, not notarized), which `tool/bundle_node.dart` fetches on a Mac; GitLab's macOS runner runs the acceptance tests with it. It serves the iOS tests' chain (an iOS app can't start a program, so it never bundles one), and the Mac app runs it as its own node, as on Windows and Linux. The chains `demo-chain` builds have empty blocks: a test that needs transactions on the chain before it starts sends them and lets the node mine them.
7. **The phones' storage path isn't tried on a device.** On Android and iOS the local copy goes under the app's cache folder (`path_provider`'s `getApplicationCacheDirectory`, in `chainCacheBase`): not the support folder, which device backups include, since the copy never leaves the device. The system may clear it when storage runs short, and the copy is then downloaded again. An earlier copy in the temp folder is moved along. Only the choice of folder is unit-tested; a build on a phone should confirm it.
8. **Transaction signatures in blocks aren't checked.** Merkle roots, filters and PoW are. A block's validity rests on the proof-of-work majority.
9. **The app's own node works in built Windows and Linux apps; macOS isn't tried.** One test, `tool/desktop_smoke_test.dart`, tries the packaged app (the folder a user unpacks) the same way on both, and the release jobs run it before packaging what's released: (1) the app starts, makes its "Murmur" window and runs its node as a child, never connects to that node (the test first sees a connection of its own to the node's ports, then watches for one of the app's), and closing the window stops both; (2) after the app is killed, the next start stops the node left behind and runs a new one; (3) with `--wallet-storage`, a wallet is saved through the system's secure storage, found again, unlocked only by its passphrase and removed (`integration_test/wallet_storage_test.dart`, inside the app with its real plugins). The user asked for that: what was tried by hand becomes a test, written once. What differs between the systems is in its `Desktop` classes:
   - **Linux** needs a session of its own, which `tool/linux_session.sh` makes (a throwaway home folder, a session bus with an unlocked keyring, a display without a screen); the test refuses to run without it. All three checks run, locally (WSL) and in releases.
   - **Windows** has no throwaway session: the app keeps its settings and wallet under the user's `%APPDATA%`, so the test refuses to run where those folders exist and removes them afterwards. It therefore runs on the release runner, not on a machine where the app is used; `--check-system`, `--close-window` and `--clients-of <pid>` try its system-specific parts anywhere.
   - **The Windows release runner** (GitLab's, Windows Server 2022) is a server system, and it took v0.2.1 to v0.2.12 to learn what it lacks: Visual Studio's ATL (the job installs it); a desktop (the app's window is found and closed by its handle, hidden or not); the Visual C++ runtime (so the app is tried as packaged, which carries it); `OPENGL32.dll` and, with no graphics card, software Direct3D, without which the engine can't draw (`tool/fetch_test_graphics.ps1` puts Mesa's OpenGL and Microsoft's WARP package beside the tried copy, pinned by SHA-256; the job checks the released package holds none of them); and Windows' data protection (DPAPI) for its account, which the wallet's storage encrypts with ("Access is denied"). So there checks 1 and 2 run, and check 3 is reported as not tried: the test asks Windows itself first, and only a refusal by Windows skips it. It needs a runner with a logged-on user. Before starting the app the test lists libraries the app loads that the system lacks (exit code 3), and a failure prints the app's own output.
